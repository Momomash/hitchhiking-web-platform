# Веб-платформа как легаси: данные, визуализации и факт-чек для доклада

Материалы к докладу «Самое большое легаси, с которым мы работаем — веб-платформа». Дата сбора данных — **17 августа 2026**. Каждое число, дата и сильное утверждение в этом документе снабжены ссылкой на первичный или авторитетный источник (WHATWG, W3C, TC39/Ecma, WHATWG/W3C living standards, wpt.fyi API, GitHub API, MDN, web.dev, IETF RFC). Там, где первичного источника найти не удалось, это явно помечено как «спорно» или «по вторичным источникам», с рекомендованной безопасной формулировкой для сцены.

---

## Executive summary

1. **Тезис доклада подтверждается данными без натяжек.** Веб-платформа не развивается по единому централизованному роадмапу. Экосистема (библиотеки, фреймворки, паттерны) регулярно закрывает реальные точки боли первой; платформа годы спустя превращает часть этих практик в кроссбраузерные, безопасные и доступные примитивы. Цена — легаси и сложность (несколько поколений API для одной и той же задачи), результат — совместимость, работающая во всём мире без привязки к одному вендору.
2. **Часть 1 (координация)** показывает, что сама *способность* индустрии договариваться и проверять совместимость — не постоянная величина, а то, что строилось десятилетиями: от «browser wars» без единой метрики (1995–2001) до Interop — ежегодного публичного соглашения всех вендоров о конкретных зонах совместимости (с 2022) и Baseline — единого статуса «можно использовать» (с 2023). Число исполняемых тестов Web Platform Tests выросло примерно в 2,6 раза с 2018 по 2026 год (с ≈25,2 тыс. до ≈65,3 тыс. в одном прогоне Chrome stable) — [wpt.fyi API](https://wpt.fyi/api/runs).
3. **Часть 2 (lag)** — по 7 отобранным «честным» кейсам медиана разрыва между заметным экосистемным workaround и нативной кроссбраузерной альтернативой (Baseline newly available) составляет **9,1 года** (диапазон 2,6–14,5 года; на полной выборке из 11 количественно измеренных кейсов диапазон 2,6–15,9 года). Важно: это не доказательство того, что «платформа копирует библиотеки» — годы не подразумевают строгой причинности, только то, что спрос в экосистеме проявляется раньше, чем платформа успевает предложить нативный эквивалент.
4. **Часть 3 (факт-чек)** нашла несколько мест, где интуитивная/из памяти формулировка про 2026 год неверна или неполна — в первую очередь про Temporal (Stage 4, но не отгружен в Safari), Popover API (newly, но не widely available), customizable `<select>` (не Baseline вообще), Prompt API (Chrome отгрузил, но Mozilla и WebKit формально против) и WebMCP/A2UI (это ранние proposal/open-project, не стандарты). Все 16 тезисов, вердикты и безопасные формулировки — в разделе «Факт-чек» ниже и в отдельном файле `fact-check-web-platform-talk.md`.

## Визуализация 1 — Таймлайн механизмов координации

**Файл:** [`web-platform-coordination-timeline.svg`](./web-platform-coordination-timeline.svg) / [`.png`](./web-platform-coordination-timeline.png) · данные: [`web-platform-coordination-timeline.csv`](./web-platform-coordination-timeline.csv), рост WPT по годам: [`web-platform-coordination-wpt-growth.csv`](./web-platform-coordination-wpt-growth.csv)

### Тип графика и логика выбора

Горизонтальная лента-таймлайн (lollipop/stem chart) с вехами, сгруппированными по 6 категориям (цвет = тип механизма: исторический контекст, спецификации и органы, тестирование/conformance, Interop/Compat, координация серверных рантаймов, сигналы совместимости). Такой формат выбран вместо, например, столбчатой диаграммы, потому что сообщение — это **последовательность появления механизмов координации**, а не сравнение величин; лента с вехами читается за секунды и не требует легенды для каждой точки (метка стоит прямо у события).

### Методология

Все даты и числа взяты из первичных/авторитетных источников: WHATWG, W3C, Ecma/TC39, публичный API wpt.fyi, GitHub API (даты создания репозиториев), MDN, web.dev. Там, где у механизма нет единой «даты основания» в первоисточниках (характерный случай — Web Platform Tests: репозиторий создан в 2012, консенсус-проект — с 2014, миграция CSS-тестов — 2017), на графике и в этом отчёте используется диапазон, а не одна точка — это сознательное решение против ложной точности. Это иллюстративные вехи координации, а не строгая причинно-следственная цепочка одного централизованного плана.

### Спикерские заметки

- Хронология не про «у кого приоритет», а про то, что сама СПОСОБНОСТЬ индустрии договариваться и проверять совместимость появлялась постепенно, а не была дана изначально.
- Если из зала спросят «а где Interop 2020?» — такого года не было; это частая путаница с Compat 2021, который был первым предшественником Interop ([раздел «Не найдено» части 1](#не-найдено--под-вопросом-часть-1)).
- Рост WPT — не «число фичей платформы», а число исполняемых тестов в одном прогоне Chrome stable (методика: первый прогон в окне 10 января – 20 февраля каждого года, [wpt.fyi/api/runs](https://wpt.fyi/api/runs)); проседание 2020→2021 (42 027 → 39 954) — инфраструктурный артефакт состава прогона, а не удаление тестов.
- Текущий масштаб (авг. 2026): 169 449 тестовых записей в манифесте WPT, из них 53 638 — импортированные файлы Test262; «чистых» веб-тестов ≈74,6 тыс. ([WPT release manifest](https://github.com/web-platform-tests/wpt/releases)).

### Источники (полный список)

Собраны в [`web-platform-coordination-timeline.csv`](./web-platform-coordination-timeline.csv), колонка `source_url`; исходное исследование — `research/part1_coordination.md`.

### Ограничения графика

- Год основания Can I Use не показан на графике как отдельная веха именно из-за спорности датировки (см. «Не найдено» ниже) — использован только как контекст в тексте доклада, не как точка данных.
- Точный подсчёт focus areas в Interop по годам отличается в зависимости от методики (README репозитория даёт одни числа, отдельные посты вендоров — другие); на графике показан только факт существования и год, без чисел focus areas.
- Даты вендорных расширений эпохи browser wars (`<blink>`, `<marquee>`, `document.layers`) не подтверждены первичными источниками того времени — на графике эта веха показана как диапазон 1995–2001 со ссылкой на WaSP, без точных дат отдельных расширений.

### Не найдено / под вопросом (часть 1)

1. Точный год основания WPT — первичного единого утверждения нет (см. таблицу выше, рекомендован диапазон 2012–2017).
2. Год запуска Can I Use — официальная страница About даты не содержит; 2008 год встречается только во вторичных источниках, первичный якорь — дата создания репозитория данных, 22.01.2012.
3. «Interop 2020» — отдельной инициативы с таким названием не существовало.
4. Число focus areas Interop 2023 — 26 по официальному README, но WebKit описывает то же как «18 новых + 5 перенесённых».
5. Дата RFC 7230 (ревизия HTTP/1.1) не подтверждена загруженной страницей в этом исследовании — для доклада безопаснее не называть 2014 год без дополнительной проверки.
6. Точная дата Acid2 (13 апреля 2005) подтверждена только вторичным источником (Wikipedia).

## Визуализация 2 — Разрыв «workaround → нативный стандарт»

**Файл:** [`workaround-to-standard-lag.svg`](./workaround-to-standard-lag.svg) / [`.png`](./workaround-to-standard-lag.png) · данные: [`workaround-to-standard-lag.csv`](./workaround-to-standard-lag.csv)

### Тип графика и логика выбора

Горизонтальный dumbbell/lollipop-график: для каждого кейса — точка «экосистемный workaround» (терракотовый), точка «нативная возможность, Baseline newly available» (бирюзовый) и соединяющий их отрезок с числом лет разрыва справа. Формат выбран за формат-3 «heatmap» из ТЗ, потому что после проверки данные оказались достаточно чистыми: по всем 7 отобранным кейсам есть надёжная дата workaround, надёжная дата платформенной вехи и объяснимый в одном предложении разрыв — heatmap скрыл бы именно эту наглядность «от — до».

### Методология

- **Дата workaround** = первая публичная версия доминирующего инструмента/паттерна (дата первой публикации в npm-реестре или дата создания публичного репозитория). Это **нижняя граница**: реальное массовое распространение обычно наступает на 1–2 года позже, поэтому все посчитанные lag'и в этом отчёте скорее **завышены** — то есть смещены не в пользу тезиса «экосистема очень быстрая», а наоборот, консервативны против него.
- **Дата нативной возможности** = Baseline *newly available* (поддержка во всех основных браузерных движках одновременно), источник — [webstatus.dev](https://webstatus.dev/) / [web-features](https://web-platform-dx.github.io/web-features-explorer/), сверка по [Can I Use](https://caniuse.com/). Отдельно в CSV указана дата *widely available* (+30 месяцев) там, где она уже достигнута.
- **Lag** = разница в годах между датой workaround и датой Baseline newly available.
- **Честность сравнения** (высокая / средняя / низкая) — решают ли workaround и нативная возможность одну и ту же задачу в сопоставимом объёме. В основной график попали только кейсы с честностью **высокая** или **средняя**; кейсы с честностью **низкая** осознанно исключены из сравнения количеств (см. ниже).

### Качественные кейсы (не для количественного сравнения)

- **Temporal vs Moment.js** — разрыв **открыт**: Safari до сих пор (авг. 2026) не отгрузил Temporal, поэтому в вебе без полифила его использовать нельзя, хотя TC39 присвоил Stage 4 в марте 2026. Хороший контрпример к тезису «платформа всегда догоняет» — здесь она пока не догнала.
- **Customizable `<select>` vs react-select и др.** — разрыв **открыт и растёт**: Baseline = limited, реализовано только в Chromium (апрель 2025), Firefox выключено по умолчанию, Safari только в бете 27.
- **`@scope` vs BEM/CSS Modules/CSS-in-JS** — честность низкая: `@scope` закрывает только selector scoping, а не всё, что делают полноценные методологии/инструменты изоляции стилей. Формальный lag 15,9 года посчитан, но сравнение по объёму задач нечестное — использовать с явной оговоркой или не использовать вовсе.
- **Custom Elements + Shadow DOM vs React/Vue** — честность низкая по той же причине: React/Vue решают значительно более широкий класс задач, чем нативная компонентная модель.

### Спикерские заметки (критично — обязательная рамка)

**Никогда не говорить**, что «платформа украла идею у библиотеки» или что workaround «стал» стандартом. Корректная формулировка: *экосистема часто демонстрировала устойчивую потребность раньше, чем платформа могла превратить её в кроссбраузерный, безопасный и доступный примитив*. Годы на графике не подразумевают строгой причинно-следственной связи — используйте обороты «потребность проявилась в экосистеме», «паттерн стал распространённой практикой», «платформа позже предложила нативный механизм».

- Медиана 9,1 года — это медиана по годам первой публикации инструмента, а не по годам массового внедрения; реальный воспринимаемый пользователями разрыв, скорее всего, **меньше**, потому что дата workaround в методологии — нижняя граница.
- Единственный «быстрый» кейс — Container Queries (2,6 года) — тоже с оговоркой: ResizeObserver сам является платформенным API, поэтому по-настоящему «полный» разрыв (от JS element-query библиотек 2013–2015 годов) может быть больше.
- Если спросят про Custom Elements/React или BEM/`@scope` — это специально исключённые кейсы (честность «низкая»), потому что библиотека и платформенный примитив решают задачи разного объёма — прямое сравнение было бы нечестным.

### Возможные возражения из зала и ответы

| Возражение | Ответ |
|---|---|
| «Разве это не значит, что платформа просто копирует индустрию с опозданием?» | Нет — платформа решает более узкую и при этом более требовательную задачу: не «повторить API библиотеки», а сделать эквивалент безопасным, доступным (a11y) и работающим во всех движках без установки зависимостей. Это другая по природе работа, которая объясняет часть задержки. |
| «А как же случаи, когда платформа опередила экосистему?» | Такие случаи есть, но не они были предметом этого исследования (задача — измерить именно разрыв там, где экосистема была первой). Упоминание сделает доклад честнее: не «платформа всегда позади», а «в измеренной выборке из явных workaround-кейсов платформа была позже». |
| «Данные не занижены специально в пользу тезиса?» | Наоборот: дата workaround — это нижняя граница (дата первой публикации), а не дата массового внедрения, которая обычно на 1-2 года позже. Если что-то и искажено методологией, то в сторону завышения лага, а не занижения. |
| «Temporal и customizable select — почему их нет в основном графике?» | Потому что у них ещё нет даты закрытия разрыва (платформа ещё не отгрузила решение во всех движках) — их корректно показывать как открытые/растущие разрывы, а не как завершённые кейсы с фиксированным числом лет. |

### Ограничения графика

- Выборка из 7 кейсов не претендует на статистическую репрезентативность всей платформы — это отобранные иллюстративные кейсы с наиболее чистыми данными.
- Ось X показывает годы workaround и Baseline newly available, но не показывает промежуточные вехи (например, первую реализацию в одном браузере) — это сознательное упрощение ради читаемости на слайде; более детальные даты есть в CSV и в `research/part2_lag_cases.md`.

## Факт-чек

Полная таблица (16 тезисов, вердикт, риск, рекомендованная формулировка для сцены, источник) — отдельный файл [`fact-check-web-platform-talk.md`](./fact-check-web-platform-talk.md). Ключевые находки, которые стоит проверить перед докладом ещё раз лично:

1. **Temporal** — Stage 4 c марта 2026 (не Stage 3), но Safari не отгрузил даже в версии 27 — использовать в вебе кроссбраузерно нельзя ([Can I Use](https://caniuse.com/temporal)).
2. **`@scope`** — кроссбраузерно только с 9 декабря 2025 (Firefox 146 закрыл матрицу последним) — некоторые трекеры до сих пор показывают устаревший статус ([Firefox 146 release notes](https://www.mozilla.org/en-US/firefox/146.0/releasenotes/)).
3. **Popover API** — newly available с 27 января 2025, но widely available ожидается только в июле 2027 — говорить «широко доступен» пока нельзя ([web-features explorer](https://web-platform-dx.github.io/web-features-explorer/features/popover/)).
4. **Customizable `<select>`** — не Baseline вообще: Chrome/Edge 135, Safari только в бете 27, Firefox за флагом ([MDN](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select)).
5. **Prompt API** — отгружен в стабильном Chrome 148, но Mozilla заняла позицию negative, а WebKit — oppose; консенсуса вендоров нет ([mozilla/standards-positions #1213](https://github.com/mozilla/standards-positions/issues/1213), [WebKit/standards-positions #495](https://github.com/WebKit/standards-positions/issues/495)).
6. **WebMCP** — Draft Community Group Report (не стандарт), origin trial с Chrome 149 ([Chrome blog](https://developer.chrome.com/blog/ai-webmcp-origin-trial)).
7. **A2UI** — открытый проект Google (v0.8, public preview), не документ органа по стандартизации, несмотря на самоназвание «open standard» ([Google Developers Blog](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)).
8. **WinterCG → WinterTC** — это не переименование, а перенос работы из W3C Community Group в Ecma International TC55, потому что CG не может публиковать формальные стандарты ([W3C announcement](https://www.w3.org/community/wintercg/2025/01/10/goodbye-wintercg-welcome-wintertc/)).
9. **CORS → SPA** — риск ложной причинности: SPA-паттерны (Gmail, Maps) появились раньше CORS Recommendation (2014); корректная формулировка — CORS снял ограничение, а не «породил» архитектуру.
